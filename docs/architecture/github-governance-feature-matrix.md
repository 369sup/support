# GitHub governance feature matrix

Verified against the linked GitHub Docs on 2026-07-28. `Implemented` means the
Support product contract is active and has a production PostgreSQL path.
`Excluded` means the behavior is intentionally outside Support's non-code
governance boundary; the reason is stated in the same row.

| Area | GitHub Docs source | Disposition | Support contract or reason |
| --- | --- | --- | --- |
| Enterprise creation and first owner | [Creating an enterprise account](https://docs.github.com/en/enterprise-cloud@latest/admin/managing-your-enterprise-account/creating-an-enterprise-account) | Implemented | `/enterprises/new` creates a standard enterprise, direct membership, and owner role atomically. Billing, trials, sales-assisted provisioning, SAML, SCIM, and Copilot licensing are excluded product domains. |
| Enterprise organizations | [Adding organizations to your enterprise](https://docs.github.com/en/enterprise-cloud@latest/admin/managing-accounts-and-repositories/managing-organizations-in-your-enterprise/adding-organizations-to-your-enterprise) | Implemented | Enterprise owners can attach a standalone organization; a database uniqueness constraint prevents simultaneous ownership by two enterprises. Email invitation, cross-enterprise transfer, billing, Sponsors, SAML, and SCIM effects are excluded. |
| Organization creation and ownership | [Creating a new organization from scratch](https://docs.github.com/en/organizations/collaborating-with-groups-organizations-and-teams/creating-a-new-organization-from-scratch) | Implemented | `/organizations/new` creates the organization and its first owner in one transaction. A database trigger prevents removal or demotion of the final active owner. |
| Organization member roles and outside collaborators | [Roles in an organization](https://docs.github.com/en/organizations/managing-peoples-access-to-your-organization-with-roles/roles-in-an-organization) | Implemented | Owner/member invitations, outside-collaborator lifecycle, predefined organization-role assignments, and direct repository grants are active. Billing manager, security products, Apps management, moderation, and code-specific permissions are excluded. |
| Custom organization roles | [About custom organization roles](https://docs.github.com/en/organizations/managing-peoples-access-to-your-organization-with-roles/about-custom-organization-roles) | Excluded | The active catalog contains only GitHub-defined predefined roles. Arbitrary permission bundles remain excluded until each permission has an approved non-code capability contract; the architecture catalog therefore keeps role-definition events planned rather than exposing a scaffold. |
| Visible and secret teams | [About organization teams](https://docs.github.com/en/organizations/organizing-members-into-teams/about-teams) | Implemented | Team create/update/delete, membership, maintainer, visible/secret visibility, single-parent hierarchy, no cycles, and inherited repository access are active. Database and domain rules prohibit nesting secret teams. Mentions, notifications, review requests, CODEOWNERS, and IdP sync are excluded. |
| Repository roles | [Repository roles for an organization](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization) | Implemented | Read, triage, write, maintain, and admin participate in highest-effective-permission calculation across owner, base, direct, team, and inherited grants. Git content, branches, pull requests, Issues, Actions, releases, wiki, packages, Pages, rulesets, and security features are excluded. |
| Repository lifecycle | [Managing repository settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings) | Implemented | Empty repository identity creation, rename, profile, visibility, archive/unarchive, soft delete, and restore are active. Git initialization, templates, forks, imports, and code settings are excluded. |
| Repository transfer | [Transferring a repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/transferring-a-repository) | Excluded | Cross-owner transfer has consequences for forks, issues, pull requests, Git URLs, Pages, Actions, packages, security, and redirects, all outside the approved non-code boundary. |
| Repository custom roles | [Managing custom repository roles](https://docs.github.com/en/enterprise-cloud@latest/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/managing-custom-repository-roles-for-an-organization) | Excluded | GitHub custom repository roles chiefly extend code, review, security, and workflow permissions that Support excludes. Support retains the five ordered base roles for its non-code administration decisions and does not expose an inert custom-role editor. |
| Repository custom properties | [Managing custom properties for repositories](https://docs.github.com/en/organizations/managing-organization-settings/managing-custom-properties-for-repositories-in-your-organization) | Implemented | Organization-owned schemas, text/single-select/multi-select/boolean validation, required/default values, batch assignment, visibility-aware reads, and property search are the active contract. Ruleset targeting is excluded. |
| Organization base permission and app-access policy reads | [Managing organization settings](https://docs.github.com/en/organizations/managing-organization-settings) | Implemented | Server-side policy queries persist base repository permission plus OAuth/GitHub App access constraints. Browser Data API access remains disabled. |
| Enterprise policy inheritance for repository creation, visibility, deletion, transfer, team creation, and grants | [About policies for your enterprise](https://docs.github.com/en/enterprise-cloud@latest/admin/enforcing-policies/enforcing-policies-for-your-enterprise/about-enterprise-policies) | Excluded | The repository does not yet define one complete, source-backed mutation contract for this cross-context policy set. The product fails closed at authorization boundaries rather than presenting policy controls that are not enforced by every mutation. Billing, Actions, security, and Copilot policies are also outside scope. |
| Audit log | [About the audit log for your enterprise](https://docs.github.com/en/enterprise-cloud@latest/admin/monitoring-activity-in-your-enterprise/about-the-audit-log-for-your-enterprise) | Implemented | Server-side append-only audit records support role-aware list, filters, cursor pagination, and event details. Git, billing, security, and external streaming events are excluded; secrets and credentials are never payload fields. |

## Global exclusions

Git files and history, commits, branches, tags, releases, forks, wikis, pull
requests, Actions, Issues, Discussions, Projects, Packages, Codespaces,
security scanning, Marketplace, billing, and documentation-product behavior are
excluded even when a linked GitHub page mentions them. Repository permissions
retain the GitHub role names only to order non-code administrative capability;
they do not activate the excluded products.
